# W0 磁盘索引、恢复与性能验证

日期：2026-08-02

## 设计结论

- 完整文本按 65,536 个 UTF-16 code unit 分段，避免把整书加载为单个字符串；
- 16 个磁盘桶记录 `bigram hash → candidate segment`，查询回读候选分段做精确匹配，哈希碰撞不会产生假命中；
- 查询最长 256 个 UTF-16 code unit，并读取相邻分段处理跨界命中；
- 每个已写分段更新 checkpoint；进程中断后校验源 SHA-256，从已提交分段续建；
- 未完成 revision 不写入 `ACTIVE`；完成目录和 `ACTIVE` 均要求同文件系统原子移动；
- 旧 revision 保留可读，可用于规则切换失败时回滚；
- 截断 postings 桶、错误 magic/版本、缺失分段和 source/revision 冲突会被拒绝。
- 章节目录最多保存 20,000 项；超过时 manifest 和构建结果显式标记截断，Android 给出提示，但正文分段与全文搜索继续完整建立；没有该尾部标记的旧 manifest 按“未截断”兼容读取。

## 正确性与失败恢复

`CorePrototypeTest` 当前共 25 个场景通过，其中磁盘索引覆盖：

1. 跨分段查询与全局字符偏移；
2. Unicode/emoji 查询；
3. 磁盘窗口回读后局部位置映射回全局锚点；
4. v1→v2 原子 ACTIVE 切换，v1 仍可回滚读取；
5. 相同 revision 指向不同内容时拒绝复用；
6. 第一分段后注入 IOException，未发布 ACTIVE；第二次构建从 checkpoint 续建并可查询；
7. 截断 postings 桶被拒绝打开。
8. 超过 20,000 个疑似章节时目录有界并显式标记截断，全文搜索仍覆盖被截断目录之后的正文；旧 manifest 继续可读。

## 主机基准

环境：OpenJDK 17.0.15，`-Xms32m -Xmx128m`，合成 UTF-8 文本，20,000 章。以下是宿主机算法证据，不替代 Android/Harmony 真机 release 数据。

| 数据集 | 源文件 | 索引大小 | 分段 | 构建 | 查询 20 条 | 最大 RSS |
|---|---:|---:|---:|---:|---:|---:|
| 10MB / 20k 章 | 10,485,790 B | 8,005,467 B | 56 | 895ms | 4.78ms | 未单独采集 |
| 100MB / 20k 章 | 104,857,613 B | 72,426,485 B | 547 | 6,540ms | 4.65ms | 150,216KB（146.7MiB） |
| 300MB / 20k 章 | 314,572,846 B | 215,584,071 B | 1,637 | 18,605ms | 62.27ms | 148,208KB（144.7MiB） |

100MB 在受限堆配置下满足方案的宿主机目标：索引 `<10s`、最大 RSS `<180MB`。300MB 无 OOM。索引空间约为源文件的 69%–76%，仍需在真实多样文本上评估并考虑压缩。

## Android API 36 Smoke

- 真实 SAF 导入 `jingdu-sample.txt`；
- 完整索引就绪：10 章、1 分段、73.4ms；
- 磁盘全文搜索 `TXT` 命中字符位置 13，并回读阅读窗口；
- 章节窗口异步加载，第二章全局锚点为 44；
- TTS 起点使用“全局锚点 - 窗口起点”映射，范围回调再恢复为全局锚点；
- 导入后强制停止应用并冷启动，无需重新进入 SAF；1.35s 后恢复相同 revision、阅读窗口和已发布完整索引；
- 最近 300 行 `AndroidRuntime:E` 为空。

## 开放项

- 真机 release 复测 100/300MB 的构建时间、RSS、耗电和前后台调度；
- 已发布索引的 Android 进程重启恢复通过；“索引构建中被系统杀死”的真实续建仍只有注入式核心测试；
- 低空间、源文件删除、索引文件位翻转和旧 revision 回收策略；
- postings 压缩、批量查询和更大规模真实语料的章节误报率；
- HarmonyOS 同格式读写与原子移动能力。

结论：磁盘索引核心和 Android 主路径为 `partial-pass`；宿主机 100MB 性能目标通过，设备端 Gate 仍未关闭。
